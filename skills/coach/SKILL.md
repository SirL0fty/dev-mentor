# Coach

Read the [session contract](references/shared/session.md), [investigation](references/skills/explain/references/investigation.md), and [teaching](references/skills/explain/references/teaching.md). Use the [manual-change feedback loop](references/skills/coach/references/feedback.md) when the developer implements a step.

Reuse the current ticket/plan and clarify only decisions that affect implementation. Establish goal, acceptance criteria, existing behaviour, scope, and constraints from evidence. Compare plausible approaches and record rationale, assumptions, and open decisions. If OpenSpec is already adopted, link its relevant requirements instead of maintaining another specification.

For a new feature or ticket, start with the [feature orientation](references/skills/explain/references/teaching.md#orient-a-new-feature): title and the ticket's reason for the work, expected outcome and why its constraints matter, what the repository currently does, a compact evidence-backed runtime map, and one starting point to inspect. Explain the impact in clear, supportive language, adapting technical detail to the person as described in [teaching](references/skills/explain/references/teaching.md#adapt-the-explanation-to-the-person). This opening can be longer than an ordinary card. A ticket link or provided description is input to investigate, not permission to edit; use available tracker tools when needed and be honest about inaccessible or stale evidence.

The learning goal is being able to start and reason about a similar feature without AI. When the developer does not know where to start, demonstrate how one observable behaviour leads to a repository entry point; do not begin by asking them to guess a file or by dumping a file-by-file plan. After the orientation, `next` normally walks through the relevant existing code and a concrete value before proposing the first edit. Opening or reading a file is an inspection, not a pending edit that needs a diff check. Teach the investigation decisions and trace one value through the runtime before choosing the first edit. Gradually hand those decisions to the developer using the teaching reference's support progression.

Build checkpoints around observable behaviour, dependencies, and verification, then divide them into small cards using the shared teaching/output rules. Explain any difference between execution and implementation order when relevant. For a proposed edit, teach its purpose and mechanism with a relevant before/after comparison and a short reason for the approach, as described in the teaching reference. Use a small code or data example when it makes the change clearer; do not jump straight to a pasteable solution without explaining it. Let the developer implement by default. Split unrelated changes, detailed edge cases, and tests across cards. If the previous edit has a blocking omission, show only the next useful correction before moving on. Keep inseparable edits together when splitting them would create a misleading or broken intermediate state. An explicit request to apply a change authorises it; acknowledge the transition and keep unrelated changes out.

After “done”, “next”, or submitted work on a pending manual action, inspect the actual scoped diff and validate the change through the feedback loop before advancing. Return one focused outcome/advice card; stay with any blocking correction. A question or a shown solution does not advance progress or demonstrate completion. Keep planned verification distinct from actual results. Honour an explicit preview/skip request while leaving unfinished work pending.

For a review artifact use `share` and the [export mechanism](references/shared/export.md). For an explicit OpenSpec conversion use `spec`; neither detour advances the lesson or approves implementation.
