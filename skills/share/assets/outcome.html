Cache layer decision

Status: Proposed Debate: agreed · conditional

For: Sam, who asked the original question. Purpose: report the arguments, what was agreed and what is still open. This is not a request to approve a build plan.

Bottom line

All three reviewers agreed to recommend an in-process cache with a 60-second expiry, on condition that a load test confirms memory use.

Model agreement is a recommendation. It is not a tested result or approval to build.

Context

Should the items API add a cache, and if so, where? Responses must stay under 200 ms at peak.

Added during the session: the catalogue is reloaded nightly, so data older than a day is never valid.

Where they disagreed, and what changed

A · Shared or in-process cache?

Before

A wanted Redis; B and C wanted in-process.

→

After

In-process, with a 60-second expiry. A agreed once stale reads were shown to be harmless here.

What changed the call

B showed the nightly reload makes cross-instance staleness irrelevant (src/jobs/reload.ts:12).

Claims that were corrected

  • C said the API has no rate limit. It does: src/middleware/limit.ts:8.

Decision

  1. Add an in-process cache with a 60-second expiry.

Consequences

  • Each instance may serve data up to 60 seconds old. Accepted because the catalogue only changes nightly.

Alternatives considered

  • Redis: rejected for now; reconsider if instances need shared state.

Still open

No reviewer objects to the conditional recommendation. That is not the same as nothing being open.
